# Проект: замена FOG для Windows-клиентов (рабочее название FOGs)

Статус: обсуждение, кода нет. Документ фиксирует принятые решения и открытые вопросы.

## 1. Цель

Самодостаточный сервер развёртывания образов Windows на ПК (компьютерный клуб).
Из FOG берём идею «хост → задача → агент», образы с блочным копированием
(только занятые блоки) и multicast. Убираем зависимость от Linux-компонентов
и неудобный интерфейс.

## 2. Принятые решения

| Тема | Решение |
|---|---|
| Клиенты | Только Windows. Среда агента: обычный WinPE (лицензия не нужна, по словам заказчика) |
| Загрузка | Только UEFI (Legacy пока не поддерживаем) |
| Идентификация хоста | По MAC-адресу. Все машины идентичны, различие только в MAC |
| Образ | Блочный, по принципу partclone: копируются только занятые кластеры |
| Multicast | Нужен с первого этапа (важная оптимизация) |
| Сервер | Один самодостаточный бинарник, работает на Linux и Windows Server |
| Язык | Go (сервер и агент): статический бинарник годится для WinPE, кросс-компиляция |
| Сборка | Через WSL-дистрибутив `claude` (см. глобальный CLAUDE.md), на хосте Windows ничего не ставим |
| Совместимость с CCBoot | Режим CCDisk (см. раздел 3) |
| DHCP | На первом этапе не трогаем: next-server и bootfile задаются вручную на MikroTik. proxyDHCP — позже, как опция |
| TFTP | Обязателен при любом варианте: UEFI получает загрузочный файл только по TFTP. Порт 69 на сервере CCBoot занят |
| Сосуществование с CCBoot | Не ломаем: службу не останавливаем, его адреса и порты не занимаем, `SO_REUSEADDR` и wildcard на 67/69/4011 не используем |

## 3. Контекст: CCBoot / CCDisk

По страницам ccboot.com (маркетинговые, детали могут быть неполными):

- CCDisk — режим CCBootCloud: Windows остаётся на **локальном SSD** каждого ПК,
  сервер отдаёт только общий игровой диск (отображается как обычная буква диска).
- Образ системы по сети не стримится. Нужны игровой диск и write-back диск, образ-диск не нужен.
- Кэширование (RAM + SSD) описано на стороне сервера. Клиентский блочный кэш в источнике не упомянут.
- При включении CCDisk CCBoot **останавливает** свои TFTP, DHCP и DHCP-proxy.
  *(На практике не подтвердилось: на сервере клуба CCBoot держит 67/69/4011 — см. §11.)*
  Следовательно, наш сервер может сам владеть PXE (DHCP/proxyDHCP, TFTP, HTTP).
  Одновременно с diskless-режимом на том же сервере наш PXE работать не сможет.
- Транспорт CCDisk в источнике не назван (iSCSI указан только для diskless-режима).

Наша задача: развёртывание и захват **системного диска**. Игровым диском занимается CCDisk.
В образ заранее ставится клиент CCDisk. Post-deploy агент на первом этапе не нужен.

## 4. Как устроен FOG (изучено, исходники в `reference/`)

- «Агент» FOG — это ~7000 строк bash (`fos`, `funcs.sh`) в мини-Linux, поверх partclone, udpcast, sfdisk.
- Опрос сервера: клиент каждые 5 с шлёт POST на PHP (`Pre_Stage1.php`, `mc_checkin.php`),
  пока не получит `##@GO` (так устроена очередь).
- Развёртывание: `udp-receiver | zstdmt -dc | partclone.restore -O /dev/sdXN`
  (одиночное: `cat` с NFS вместо `udp-receiver`).
- Захват: `partclone.ntfs -cs /dev/sdXN | zstd | файл на сервере`.
- Таблица разделов сохраняется отдельно (`sfdisk -d`) и пересчитывается под новый диск, в этом основная часть кода.
- Multicast: серверный демон запускает `udp-sender`, ждёт `--min-receivers` клиентов или `--max-wait`.
- Формат partclone: заголовок (версия, ФС, размер блока, число блоков) → bitmap занятых блоков →
  только занятые блоки с CRC. Структуры в `reference/partclone/src/partclone.h`.

## 5. Загрузка по MAC

1. ПК грузится по PXE (UEFI), получает iPXE от нашего сервера.
   UEFI умеет только TFTP, поэтому первый файл отдаёт TFTP-сервер; всё дальнейшее идёт по HTTP.
2. iPXE запрашивает скрипт: `GET /boot.ipxe?mac=...`.
3. Сервер ищет хост по MAC и проверяет, есть ли активная задача.
4. **Задача есть:** скрипт грузит WinPE через `wimboot`. На этапе iPXE подкладываются
   агент и файл запуска (идея заказчика), поэтому пересобирать `boot.wim` под каждое изменение агента не нужно.
5. **Задачи нет:** выход на локальный диск (Windows Boot Manager). Для UEFI это `exit` из iPXE.
6. **Неизвестный MAC:** тоже загрузка с диска. MAC попадает в список «обнаружены, не зарегистрированы»
   в интерфейсе, добавляется в один клик. Автоматически ничего не разворачивается.

Нужно проверить на практике: куда именно `wimboot` кладёт дополнительные файлы внутри WinPE
и как запустить агента (`startnet.cmd` или `winpeshl.ini`).

## 6. Технические идеи для Go-реализации

- **Bitmap занятых кластеров:** `FSCTL_GET_VOLUME_BITMAP` на `\\.\C:` (без разбора NTFS `$Bitmap`).
  Читаем только занятые кластеры, сжимаем zstd (pure Go, `klauspost/compress`), пишем свой формат.
- **Формат образа:** образ диска — каталог с `manifest.json` (таблица GPT, политики разделов) и файлами `.fogs`,
  по одному на раздел с содержимым. Файл `.fogs`: заголовок (magic, версия, размер кластера, всего/занято блоков,
  размер устройства, CRC bitmap) → bitmap → независимые сжатые чанки (`[compLen][rawLen][index][crc32][данные]`).
  Независимые чанки дают параллельное сжатие и естественные «слайсы» для multicast.
  Занятые кластеры подряд образуют один поток, нарезанный по `chunkSize`, поэтому номер чанка однозначно задаёт
  его место в потоке: по нему получатель кладёт чанк на диск и запрашивает потерянный (NACK).
  CRC чанка покрывает и его заголовок, и данные. Bitmap проверяется до записи на диск: ошибка в нём означает запись не по тем смещениям.
- **Разметка диска:** нативно, через `IOCTL_DISK_SET_DRIVE_LAYOUT_EX`; расширение/сжатие тома через
  `FSCTL_EXTEND_VOLUME` / `FSCTL_SHRINK_VOLUME`. Без sfdisk и ntfsresize.
- **Multicast:** собственный протокол по образцу udpcast (слайсы, NACK от получателей, повтор отправителем).
  `udpcast` под Windows не работает. Это самая рискованная часть. Unicast по HTTP (стриминг) делаем
  первым, чтобы отладить формат образа, затем multicast.
- **Экран агента:** графический, на чистом Go. `agent/ui` рисует кадр в память (шрифты Go с кириллицей встроены, от шрифтов WinPE не зависим),
  окно на весь экран выводит его через `SetDIBitsToDevice`. C#, .NET и WebView не используем: им нужен изменённый `boot.wim`.
  Экран только показывает состояние, управление идёт с сервера. Проверено в обычной Windows, в WinPE ещё нет.
- **`boot.wim`:** берём официальный из `sources\boot.wim` на ISO Windows, индекс 1 (Windows PE), без изменений. В git и релизы не кладём.
- **Подготовка к захвату:** как в FOG, удаление pagefile/hiberfil и очистка mounted devices.
- **Статус задач:** WebSocket или long-poll вместо опроса PHP. Очередь «ждёт слот» сохраняем.
- **Хранилище:** SQLite (pure Go, `modernc.org/sqlite`), образы в файловой системе сервера. Схема обновляется миграциями по `PRAGMA user_version`.
- **Панель:** страница и JSON API в `server/web`, встроены в бинарник. Без входа, поэтому слушает только loopback, а другой адрес сервер отвергает.
  Доступ из сети клуба откроем вместе с авторизацией (вопрос 5 в §13). Ошибка базы при запросе клиента считается отказом: ПК грузится с диска.

## 7. Структура репозитория (предложение)

- `server/`: HTTP API, веб-интерфейс (`embed`), очередь задач, образы, multicast-отправитель, iPXE-скрипты, proxyDHCP/TFTP.
- `agent/`: бинарник `windows/amd64` для WinPE.
- `proto/`: формат образа и протокол multicast (общий пакет).
- `winpe/`: скрипты подготовки WinPE, iPXE и wimboot.

## 8. Модель данных (первый этап)

- **Host:** MAC (может быть несколько), имя, группа, привязанный образ.
- **Image:** путь, размер, формат, дата захвата.
- **Task:** тип (capture, deploy, multicast), хост или группа, статус и прогресс, времена.
- **Group:** набор хостов; multicast-сессия запускается по группе.

## 9. Разделы диска

- На клиенте будут все разделы, что были на эталоне.
- У каждого раздела в образе есть политика: `fixed` (размер как в образе) или `fill`
  (занять всё оставшееся место диска). По умолчанию `fill` получает самый большой NTFS-раздел
  (обычно C:), в интерфейсе можно переназначить.
- При захвате `fill`-раздел сжимается до минимума (`FSCTL_SHRINK_VOLUME`), чтобы образ влезал на диски меньшего размера.
- При развёртывании таблицу разделов строим заново: `fixed` сохраняют размер, `fill` получает остаток
  (минус хвостовые `fixed`, например Recovery). Раздел не двигаем, а размечаем с нуля, поэтому
  аналога `movePartition` из FOG не нужно. После записи блоков файловая система расширяется (`FSCTL_EXTEND_VOLUME`).
- Разделы и политики хранятся в `manifest.json`. Раздел без поля `file` (например, MSR) только создаётся, содержимое не восстанавливается.

Нужно проверить на практике: на FAT32 (раздел EFI) кластер 0 из `FSCTL_GET_VOLUME_BITMAP`, вероятно, начинается не со
смещения 0 тома, а после служебной области. Тогда такой раздел надо захватывать целиком посекторно, а не по этому bitmap.

## 10. Sysprep и имя хоста

Sysprep (generalize) — штатная утилита Microsoft, которая обезличивает установленную Windows
перед клонированием: убирает SID, имя ПК, привязку драйверов, а при первой загрузке выполняет
донастройку по `unattend.xml`. Плюсы: чистые клоны, нужно для домена. Минусы: ограниченное число
rearm, сброс части настроек, может задеть клиент CCDisk.

Решение: на первом этапе клонируем как есть. Для различий по MAC агент в WinPE после записи образа
правит имя хоста **офлайн** (загрузка реестра `SYSTEM` развёрнутого раздела, `reg load`), так что
post-deploy агент не нужен. FOG делает то же самое (`changeHostname` в `funcs.sh`).
Вопрос: нужны ли разные имена хостов, или одинаковые допустимы?

## 11. DHCP и MikroTik

**Этап 1 (принято, сейчас):** DHCP остаётся у MikroTik. `next-server` и имя загрузочного файла
задаются там вручную для тестового ПК, наш сервер отдаёт только TFTP и HTTP. Ограничение: выдавать
их нужно строго per-lease (только тестовому ПК), иначе клиенты CCBoot уедут на нас; в RouterOS 7
это делается через option-set у lease.

**Этап 2 (опция):** свой proxyDHCP. DHCP выдаёт роутер MikroTik, его не трогаем. Наш сервер работает как **proxyDHCP**:
слушает DHCPDISCOVER с опцией 60 `PXEClient` (UDP 67 broadcast) и отвечает только PXE-данными
(next-server, имя загрузочного файла), а клиент подтверждает на порту 4011. Решение принимается по MAC.

**Требование для этапа 2: ничего не прописывать на роутере** (ни next-server, ни boot-file-name). Это должно работать
на любом роутере, в том числе без доступа к DHCP-опциям (например, провайдерский). Поэтому целевой режим один:
proxyDHCP. Условие: сервер в том же L2-сегменте, что и клиенты (или есть DHCP relay), и роутер не
фильтрует broadcast. Позже добавим полноценный DHCP как отдельный режим работы.
Этап 1 сознательно нарушает это требование: ручная настройка на MikroTik допустима, пока речь идёт
о тестовом ПК и чужие клиенты не затрагиваются.
Идея на потом: Wake-on-LAN с сервера для машин, у которых появилась задача.

**Реализация (`server/dhcp`):** этап 2 сделан раньше этапа 1, потому что разработка идёт на ПК, где порты 67/69/4011 свободны.
Сервер отвечает только MAC из явного списка, остальных пишет в лог: это заменяет per-lease ограничение из этапа 1.
Прошивке UEFI отдаётся `ipxe.efi` без опции 43 (она затем обращается на 4011), клиенту с user class `iPXE` — URL `boot.ipxe`.
Нужно проверить на практике: если в сети уже отвечает другой PXE-источник (`next-server` на MikroTik, proxyDHCP CCBoot),
какой ответ выберет прошивка тестового ПК.

Проверено на реальном ПК (2026-11-05): цепочка прошивка → `ipxe.efi` → `boot.ipxe` работает.
`ipxe.efi` сразу после старта запрашивает `autoexec.ipxe` по TFTP. Если файл есть, iPXE выполняет его вместо своего автозапуска,
поэтому сервер генерирует этот скрипт: он сам вызывает `dhcp` и переходит на `boot.ipxe`, а при ошибке выходит в UEFI.

## 12. Secure Boot (включён на клиентах)

Исходный iPXE и wimboot не подписаны ключом из базы `db` прошивки. Два пути:

**А. Свой CA, подписанные iPXE и wimboot.**
Мы собираем iPXE и wimboot сами и подписываем своим ключом. Сертификат (DER/`.cer`) один раз
добавляется в `db` каждого ПК вручную в UEFI. Идея агента, подкладываемого на этапе iPXE, сохраняется.
Плюс: быстрая HTTP-загрузка. Минус: ручное добавление сертификата на каждую машину, а сброс CMOS его стирает.

**Б. Цепочка, подписанная Microsoft.**
WinPE грузится штатным `bootmgfw.efi` + BCD + `boot.wim` по TFTP (как WDS). Регистрировать
сертификат не нужно. Минусы: агент должен быть в `boot.wim` (достаточно маленького загрузчика,
который докачивает основной агент по HTTP), загрузка `boot.wim` по TFTP медленнее (нужен windowsize),
и proxyDHCP отвечает **только** хостам с активной задачей, остальные грузятся с диска сразу.
Учесть: загрузчик в ADK должен быть подписан CA, которому доверяет `db` клиентов
(переход на Windows UEFI CA 2023).

### Как клиент находит сервер с boot.wim (путь Б)

- proxyDHCP-ответ содержит `siaddr` (наш сервер), имя загрузочного файла (`bootmgfw.efi`)
  и опцию 252 с путём к BCD. Всё это приходит от нас, роутер не участвует.
- `bootmgfw.efi` берёт BCD с того же TFTP-сервера. В BCD путь к `boot.wim` задан как
  `[boot]\...\boot.wim`: `[boot]` означает «устройство, с которого загрузились», то есть наш сервер.
  IP в BCD не зашит, один BCD работает при любом адресе сервера.
- Скорость TFTP настраивается в BCD (`ramdisktftpblocksize`, `ramdisktftpwindowsize`).
- Агент в WinPE находит сервер сам: UDP broadcast «где сервер?» и ответ сервера. Адрес в `boot.wim`
  не зашивается. Это нужно проверить на практике.
- Файлы Microsoft (`bootmgfw.efi`, `boot.sdi`, `boot.wim`) в дистрибутив сервера не кладём.
  Скрипт сборки берёт их из ADK, установленного у пользователя.

Независимо от пути:
- Страница в интерфейсе для скачивания сертификата с **отображением SHA-256 отпечатка**
  (отпечаток сверяется вручную в UEFI, иначе подмена файла по незащищённому HTTP — это подмена корня доверия).
- Хранение CA: корневой ключ офлайн, подпись бинарников выполняется при сборке, а не на сервере в рантайме.
  На сервере лежит только публичный сертификат. Нужен план ротации и отзыва (`dbx`).
- Проверить, годится ли подписанный нами `wimboot` для `LoadImage` под Secure Boot.
